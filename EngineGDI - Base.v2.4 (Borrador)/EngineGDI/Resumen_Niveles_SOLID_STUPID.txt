RESUMEN DE IMPLEMENTACION DE NIVELES
Proyecto: EngineGDI

Este documento explica por que se aplicaron los cambios de niveles, como se implementaron, como funcionan dentro del proyecto y como se relacionan con los principios SOLID y con el analisis STUPID.

==================================================
1. OBJETIVO DEL CAMBIO
==================================================

Se pidió agregar un sistema de dos niveles con estas reglas:

- Nivel 1:
  - Solo asteroides
  - Solo nave roja
  - Fondo base del juego

- Nivel 2:
  - Solo asteroides
  - Solo nave azul
  - Fondo BackGround2.png

- Acceso al nivel 2 por dos caminos:
  - Al llegar a 2500 puntos
  - Al presionar Ctrl + F

La idea principal fue resolver esto sin duplicar toda la escena `Game`, respetando la arquitectura ya usada en el proyecto:
- escena principal centralizada
- pools para enemigos y balas
- factorias y callbacks para desacoplar comportamiento

==================================================
2. POR QUE SE IMPLEMENTO DE ESTA FORMA
==================================================

Se eligio una configuracion por nivel dentro de la misma escena `Game` en lugar de crear dos clases completamente separadas (`GameLevel1`, `GameLevel2`) por estas razones:

1) Ambas escenas comparten casi toda la logica:
- player
- HUD
- colisiones
- pausa
- game over
- balas
- loop principal

2) La diferencia real entre niveles es configuracional:
- fondo
- tipos de enemigos habilitados
- condicion de transicion

3) Duplicar toda la escena hubiera generado:
- mas codigo repetido
- mas riesgo de inconsistencias
- mas costo de mantenimiento

Por eso se uso una sola clase `Game` parametrizada por un enum interno llamado `NivelJuego`.

Ubicacion:
- Game.cs, lineas 11-20

3. COMO SE IMPLEMENTO
==================================================

3.1. Enum interno de niveles

Se agrego un enum interno:
- Nivel1
- Nivel2

Ubicacion:
- Game.cs, lineas 11-15

Funcion:
- Representa el nivel actual de forma explicita.
- Evita usar bools ambiguos como `isLevel2`.

3.2. Puntaje objetivo para pasar a nivel 2

Se agrego una constante:
- PuntajeObjetivoNivel2 = 2500

Ubicacion:
- Game.cs, linea 17

Funcion:
- Centraliza el valor de diseño.
- Evita repetir magic numbers.

3.3. Constructor principal y constructor interno con estado

Se dejo el constructor publico normal:
- `new Game(screenWidth, screenHeight)` arranca en nivel 1

Y se agrego un constructor privado configurable:
- nivel actual
- vidas iniciales
- score inicial

Ubicacion:
- Game.cs, lineas 39-50

Funcion:
- Permite crear nivel 1 desde cero
- Permite crear nivel 2 preservando progreso
- Permite que Retry reconstruya el nivel actual

3.4. Conservacion de score y vidas entre niveles

Se actualizo `UIManager` para aceptar:
- `initialLives`
- `initialScore`

Ubicacion:
- UIManager.cs, lineas 30-44

Funcion:
- Cuando se cambia del nivel 1 al nivel 2, no se reinician score ni vidas.
- La HUD se reconstruye con los mismos valores.

3.5. Fondo por nivel

Se reutilizo `BackgroundManager` sin modificar su logica interna.
Solo se le pasa el sprite correcto segun el nivel actual.

Ubicacion:
- Game.cs, linea 66
- Game.cs, lineas 313-317
- BackgroundManager.cs, lineas 27-40

Funcion:
- Nivel 1 usa `Textures/BackGrounds/Background.png`
- Nivel 2 usa `Textures/BackGrounds/BackGround2.png`

3.6. Restriccion de enemigos por nivel

Se extendio `EnemyPool` con dos flags:
- `incluirNaveRoja`
- `incluirNaveAzul`

Ubicacion:
- EnemyPool.cs, lineas 24-25
- EnemyPool.cs, lineas 29-42
- EnemyPool.cs, lineas 227-253

Funcion:
- Permite usar la misma pool para distintos niveles.
- No obliga a crear otra clase de pool ni a duplicar spawners.

En `Game` se pasa:
- Nivel 1:
  - `incluirNaveRoja: true`
  - `incluirNaveAzul: false`
- Nivel 2:
  - `incluirNaveRoja: false`
  - `incluirNaveAzul: true`

Ubicacion:
- Game.cs, lineas 68-82

3.7. Seleccion de enemigos segun flags

Se modifico `ElegirTipoEnemigo()` para tomar decisiones segun las banderas habilitadas.

Ubicacion:
- EnemyPool.cs, lineas 271-289

Funcion:
- Si solo esta habilitada la roja, spawnea asteroide o roja.
- Si solo esta habilitada la azul, spawnea asteroide o azul.
- Si estan ambas, mantiene el comportamiento mixto.
- Si ninguna esta habilitada, spawnea solo asteroides.

3.8. Atajo Ctrl + F para pasar de nivel

Se agrego un metodo que detecta:
- tecla Control presionada
- evento OnKeyDown de F

Ubicacion:
- Game.cs, lineas 304-310

Se integra en Input asi:
- si estas en nivel 1 y se detecta Ctrl + F, se marca una transicion pendiente

Ubicacion:
- Game.cs, lineas 113-117

3.9. Paso a nivel 2 por puntaje

Cada vez que se destruye un enemigo:
- se suman 100 puntos
- se actualiza high score
- si estas en nivel 1 y el score llega a 2500, se marca transicion pendiente

Ubicacion:
- Game.cs, lineas 191-199

3.10. Transicion real de escena

No se cambia de escena en medio de una operacion compleja de gameplay.
En lugar de eso se usa un flag:
- `shouldAdvanceToLevel2`

Ubicacion:
- Game.cs, linea 36

Funcion:
- Evita acoplar el cambio de escena al mismo evento que lo detecta.
- La escena se cambia de forma controlada en `Update()`.

Ubicacion de uso:
- Game.cs, lineas 150-153
- Game.cs, lineas 180-181
- Game.cs, lineas 298-302

3.11. Retry reinicia el nivel actual

Antes `Retry` siempre reiniciaba `new Game(screenWidth, screenHeight)`.
Ahora reconstruye el mismo nivel actual.

Ubicacion:
- Game.cs, lineas 235-242

Funcion:
- Si perdes en nivel 2, reinicias nivel 2.
- Si perdes en nivel 1, reinicias nivel 1.

3.12. Registro del fondo nuevo en el proyecto

Se agrego `BackGround2.png` al `.csproj` para que se copie al output.

Ubicacion:
- EngineGDI.csproj, lineas 172-177

Funcion:
- Si el recurso no se incluye ahi, el juego puede compilar pero el asset no estar disponible en runtime.

4. COMO FUNCIONA EN EJECUCION
==================================================

Flujo completo:

1) El juego arranca con:
- `new Game(screenWidth, screenHeight)`
- esto crea nivel 1 por defecto

Ubicacion:
- Game.cs, lineas 39-42

2) `Game` crea:
- player
- HUD
- BulletPool
- BackgroundManager
- EnemyPool

Ubicacion:
- Game.cs, lineas 50-85

3) El nivel actual decide:
- que fondo usar
- si se permite nave roja
- si se permite nave azul

Ubicacion:
- Game.cs, lineas 66-82

4) Durante el gameplay, el jugador puede pasar a nivel 2 de dos formas:
- por score >= 2500
- por Ctrl + F

Ubicacion:
- Game.cs, lineas 113-117
- Game.cs, lineas 191-199
- Game.cs, lineas 304-310

5) Cuando se detecta la condicion, no se cambia todo instantaneamente.
Primero se activa:
- `shouldAdvanceToLevel2 = true`

6) En el siguiente ciclo de `Update()`, `AdvanceToLevel2()` crea una nueva escena:
- nivel 2
- mismas vidas
- mismo score

Ubicacion:
- Game.cs, lineas 298-302

7) El nuevo `Game` de nivel 2:
- usa `BackGround2.png`
- permite solo asteroides y nave azul

==================================================
5. POR QUE FUNCIONA BIEN CON EL PARADIGMA ACTUAL
==================================================

El proyecto ya estaba organizado alrededor de:
- SceneManager
- Game como escena principal
- pools reutilizables
- fabricas
- callbacks

La implementacion nueva respeta esa idea porque:

- no rompe `SceneManager`
- no duplica `BackgroundManager`
- no crea un sistema paralelo de enemigos
- reusa `EnemyPool` como capa configurable
- mantiene a `Game` como coordinador principal

Eso hace que el cambio sea coherente con el paradigma existente en el proyecto.

==================================================
6. ANALISIS SOLID
==================================================

6.1. S - Single Responsibility Principle

Donde se cumple:

- `Game` coordina la escena y la transicion de nivel.
  Ubicacion: Game.cs, lineas 9-319

- `EnemyPool` administra pools, spawns y seleccion de enemigos.
  Ubicacion: EnemyPool.cs, lineas 6-297

- `UIManager` administra vidas y score de la HUD.
  Ubicacion: UIManager.cs, lineas 9-80

- `BackgroundManager` solo administra desplazamiento y render del fondo.
  Ubicacion: BackgroundManager.cs, lineas 8-71

Por que se cumple:
- Cada clase conserva una responsabilidad principal.
- La logica de nivel no fue metida dentro de `BackgroundManager` o `UIManager`, sino en `Game`, que es el coordinador correcto.

6.2. O - Open/Closed Principle

Donde se cumple:
- `Game` se extendio con `NivelJuego` y nuevas reglas sin reescribir todo el sistema de juego.
- `EnemyPool` se extendio con flags para cambiar composicion sin rehacer su arquitectura.

Ubicacion:
- Game.cs, lineas 11-20
- EnemyPool.cs, lineas 24-25
- EnemyPool.cs, lineas 271-289

Por que se cumple:
- El sistema se abrio a nuevos comportamientos por configuracion.
- No se requirio cambiar radicalmente cada modulo para soportar niveles.

6.3. L - Liskov Substitution Principle

Donde se mantiene:
- `SceneManager` sigue tratando a `Game` como `IScene`.
- La nueva version de `Game` sigue siendo intercambiable como escena valida.

Ubicacion:
- SceneManager.cs, lineas 19-40
- Game.cs, linea 9

Por que se cumple:
- El cambio no rompe el contrato de `IScene`.
- `Game` sigue respondiendo correctamente a `Input`, `Update` y `Render`.

6.4. I - Interface Segregation Principle

Donde se mantiene:
- El sistema sigue apoyandose en interfaces pequeñas como `IScene`, `ICollidable`, `IDamageable`.

Por que se cumple:
- La logica de nivel no fuerza a otras clases a implementar interfaces nuevas o metodos que no necesitan.

6.5. D - Dependency Inversion Principle

Donde se cumple parcialmente:
- `Game` delega comportamiento de disparo en callbacks hacia `BulletPool`.
- `EnemyPool` depende de banderas y callbacks, no del detalle interno de cada bala.

Donde no se cumple del todo:
- `Game` sigue creando concretos directamente (`Player`, `BulletPool`, `BackgroundManager`, `EnemyPool`).
- `Game` conoce rutas concretas de assets.

Ubicacion:
- Game.cs, lineas 50-85

Conclusion SOLID:
- La implementacion cumple bien SRP, OCP y LSP.
- Mantiene ISP.
- DIP esta aplicado en parte, pero todavia hay construccion directa de concretos.

==================================================
7. ANALISIS STUPID
==================================================

STUPID es una lista de anti-patrones que conviene detectar y reducir:

- S: Singleton
- T: Tight Coupling
- U: Untestability
- P: Premature Optimization
- I: Indescriptive Naming
- D: Duplication

No es algo "bueno" que se deba cumplir.
Se usa mas bien para analizar donde hay riesgos de diseño.

7.1. S - Singleton

Donde aparece:
- `SceneManager.Instance`
- `GameManager.Instance`
- `AudioManager.Instance`

Relacion con esta implementacion:
- La transicion entre niveles se resuelve usando `SceneManager.Instance.ChangeScene(...)`.

Ubicacion:
- Game.cs, lineas 230, 241, 245, 301

Lectura:
- Es practico para un proyecto pequeño.
- Pero sigue siendo un ejemplo claro de `Singleton`, que STUPID considera un riesgo si se abusa.

7.2. T - Tight Coupling

Donde se redujo:
- No se crearon dos escenas gigantes separadas con codigo copiado.
- `EnemyPool` usa parametros `incluirNaveRoja` e `incluirNaveAzul` en lugar de lógica duplicada por nivel.

Ubicacion:
- EnemyPool.cs, lineas 24-25
- EnemyPool.cs, lineas 271-289

Donde sigue existiendo:
- `Game` conoce directamente sprites, rutas y clases concretas.

Ubicacion:
- Game.cs, lineas 54-82

Lectura:
- El cambio reduce acoplamiento comparado con duplicar escenas.
- Pero todavia hay un acoplamiento moderado en la configuracion central.

7.3. U - Untestability

Donde mejora:
- Separar la regla de transicion en metodos como `CanAdvanceToLevel2`, `AdvanceToLevel2`, `IsLevel2ShortcutPressed` hace la logica mas localizable.

Ubicacion:
- Game.cs, lineas 293-310

Donde sigue costando probar:
- El uso de input global en `Engine`
- Los singletons
- El cambio de escena directo

Lectura:
- La logica quedo mejor encapsulada, pero no es un sistema plenamente orientado a testing automatizado.

7.4. P - Premature Optimization

Lectura:
- No hay una optimizacion prematura nueva en este cambio.
- Reutilizar `EnemyPool` y `BackgroundManager` no es sobreoptimizar; es reaprovechar arquitectura existente.

Conclusión:
- En este caso no se cae especialmente en este anti-patron.

7.5. I - Indescriptive Naming

Donde se hizo bien:
- `NivelJuego`
- `PuntajeObjetivoNivel2`
- `shouldAdvanceToLevel2`
- `incluirNaveRoja`
- `incluirNaveAzul`

Ubicacion:
- Game.cs, lineas 11-20 y 36
- EnemyPool.cs, lineas 24-25

Lectura:
- Los nombres nuevos son descriptivos y coherentes con el proyecto.
- Este punto esta bien resuelto en esta implementacion.

7.6. D - Duplication

Donde se evito duplicacion:
- No se crearon dos clases Game completas.
- No se duplico la logica de fondo.
- No se duplico la logica de HUD.
- No se duplico la logica del pool de enemigos.

Ubicacion:
- Game.cs, lineas 39-85
- EnemyPool.cs, lineas 208-253

Lectura:
- Esta es una de las mayores virtudes del cambio.
- Se reutilizo estructura y solo se inyecto configuracion.

Conclusión STUPID:
- Se evita fuertemente `Duplication`.
- Se mejora bastante `Indescriptive Naming`.
- Se reduce `Tight Coupling`, aunque no desaparece.
- `Singleton` sigue presente en la arquitectura global.
- `Untestability` mejora un poco, pero sigue existiendo por dependencias globales.

==================================================
8. CONCLUSION FINAL
==================================================

La implementacion de niveles se resolvio como una extension de la escena `Game` y no como una duplicacion del gameplay.

Eso fue una buena decision porque:
- mantiene el paradigma del proyecto
- minimiza codigo repetido
- permite conservar score y vidas
- aprovecha la pool de enemigos y el manager de fondo existentes
- hace que el nivel 2 sea una variacion de configuracion y no otro juego aparte

En terminos de SOLID:
- esta bien alineado principalmente con SRP, OCP y LSP

En terminos de STUPID:
- reduce duplicacion y mejora nombres
- pero sigue conviviendo con algunos singletons y acoplamiento moderado, algo esperable en la arquitectura actual del proyecto
